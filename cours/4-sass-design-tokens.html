Sass moderne

Ce que le préprocesseur apporte encore en 2026

Sass a-t-il encore sa place ?

Sass est un préprocesseur : on écrit du SCSS, un compilateur produit le CSS que lit le navigateur. Depuis, le CSS natif a rattrapé une partie de son retard.

Devenu natif

  • Variables : custom properties
  • Imbrication des règles (Baseline 2023)
  • Calculs : calc(), clamp(), min()
  • Couleurs dérivées : color-mix()

Propre à Sass

  • Modules : un fichier par composant, des noms isolés
  • Maps et boucles pour générer des classes
  • Fonctions et mixins réutilisables
  • Erreurs à la compilation, avant la mise en ligne
Notre règle : ce qui doit vivre dans le navigateur (thème, valeurs modifiables en JS) passe par le CSS natif. Ce qui sert à écrire le CSS passe par Sass.

Variable Sass ou custom property ?

Variable Sass $space-mCustom property --space-m

Dans @mediaOui : (width >= $bp-m)Non : var() est refusé dans une condition
Idéale pourPoints de rupture, listes à parcourirCouleurs, espaces, thèmes clair et sombre
Les deux se complètent : nos tokens sont déclarés en Sass (maps) puis publiés en custom properties par une boucle.

Les modules : @use et @forward

  • @use "chemin" charge un fichier une seule fois et range ses membres sous un espace de noms : tools.rem()
  • @forward réexporte les membres d'un fichier, par exemple depuis un _index.scss
  • Un partial commence par _ : il n'est jamais compilé seul, seulement chargé
  • Modules intégrés : sass:map, sass:math, sass:color…
@import est déprécié dans Dart Sass et disparaîtra en version 3. Il chargeait tout dans un espace global : collisions de noms, CSS dupliqué, ordre fragile.
Pour migrer un ancien projet : npx sass-migrator module. LibSass et node-sass sont abandonnés : seul Dart Sass (paquet sass) est maintenu.

Fonctions et mixins

// Outils Sass : ils ne produisent aucun CSS tant qu'on ne
// les appelle pas
@use "sass:map";
@use "sass:math";

$breakpoints: (
  "m": 48rem,
  "l": 64rem,
);

// Convertit une mesure de maquette en rem (16 px = 1 rem)
@function rem($px) {
  @return math.div($px, 16px) * 1rem;
}

// Requête média à partir du nom d'un point de rupture
@mixin from($name) {
  @if not map.has-key($breakpoints, $name) {
    @error "Point de rupture inconnu : #{$name}";
  }

  @media (width >= map.get($breakpoints, $name)) {
    @content;
  }
}

// Anneau de focus visible et contrasté (critère WCAG 2.4.7)
@mixin focus-ring($color: var(--color-focus)) {
  outline: 3px solid $color;
  outline-offset: 2px;
}
  • @function renvoie une valeur : rem(24px) donne 1.5rem
  • math.div remplace le /, réservé aux séparateurs CSS (grid-area: 1 / 3)
  • @mixin produit des déclarations, insérées par @include
  • @content reçoit le bloc écrit à l'appel
  • @error arrête la compilation sur un nom inconnu

Placeholders, @extend et suffixes

@use "../abstracts/tools";

// Une variante = un fond et une couleur de texte
@mixin variant($background, $color) {
  background: $background;
  color: $color;

  &:hover {
    background: color-mix(in oklch, $background, black 15%);
  }
}

@layer components {
  // Un placeholder ne produit rien tant qu'on ne l'étend pas
  %button-base {
    display: inline-flex;
    gap: var(--space-xs);
    align-items: center;
    padding: tools.rem(10px) tools.rem(20px);
    border: 2px solid transparent;
    border-radius: var(--radius-pill);
    font: inherit;
    font-weight: 700;
    text-decoration: none;
    cursor: pointer;
  }

  .button {
    @extend %button-base;
    @include variant(var(--color-primary), var(--color-on-primary));

    // &--accent devient .button--accent : propre à Sass, le
    // nesting natif ne sait pas coller un suffixe
    &--accent {
      @include variant(var(--color-accent), var(--color-on-primary));
    }

    &--ghost {
      border-color: currentcolor;
      background: transparent;
      color: var(--color-primary);
    }

    &:focus-visible {
      @include tools.focus-ring;
    }
  }
}
  • Un placeholder %button-base n'existe pas dans le CSS final
  • @extend ajoute .button à son sélecteur
  • &--accent colle un suffixe : pratique pour le nommage BEM
Avec prudence : @extend regroupe des sélecteurs éloignés et ne traverse pas les @media. Dans le doute, préférez un mixin.

Générer des classes avec @each

@use "sass:map";
@use "../tokens";

@layer utilities {
  // Une classe de marge par espace : .mt-2xs, .mt-xs… .mt-xl
  @each $name in map.keys(tokens.$spaces) {
    .mt-#{$name} {
      margin-block-start: var(--space-#{$name});
    }
  }

  // Masque un texte à l'écran sans le cacher aux lecteurs
  // d'écran
  .visually-hidden {
    position: absolute;
    inline-size: 1px;
    block-size: 1px;
    overflow: hidden;
    clip-path: inset(50%);
    white-space: nowrap;
  }
}
  • @each parcourt une liste ou une map
  • map.keys donne les noms des espaces : six classes produites
  • #{$name} : l'interpolation insère une valeur dans un sélecteur ou un nom
  • Ajouter un espace dans la map ajoute la classe, sans rien recopier
.visually-hidden masque un texte à l'écran mais le laisse aux lecteurs d'écran, contrairement à display: none.

Compiler

npm install --save-dev sass

  • --watch recompile à chaque enregistrement
  • --style=compressed minifie pour la production
  • Une erreur de compilation donne le fichier et la ligne

Avec Vite

Vite compile le SCSS dès qu'on installe sass : on écrit <link rel="stylesheet" href="/scss/main.scss"> et le serveur de développement recharge la page à chaud.
Ne modifiez jamais dist/ à la main : il est écrasé à la compilation suivante.

Design tokens et architecture

Des décisions de design nommées, partagées et versionnées

Trois niveaux de tokens

Un design token est une décision de design nommée : une couleur, un espace, un rayon. Designers et développeurs utilisent le même nom.

Primitifs

Les valeurs brutes de la charte
--palette-teal-700
« quelle valeur ? »

Sémantiques

Un rôle dans l'interface
--color-primary
« à quoi sert-elle ? »

De composant

Un réglage local
--button-background
« où l'utilise-t-on ? »
  • Un composant n'utilise jamais un primitif : passer en thème sombre ne change que les sémantiques
  • Dans Figma, ce sont les variables : relevez leurs noms dans la maquette de votre projet

Un format commun : DTCG

{
  "color": {
    "palette": {
      "teal-700": {
        "$type": "color",
        "$value": {
          "colorSpace": "oklch",
          "components": [0.48, 0.1, 185]
        }
      }
    },
    "primary": {
      "$type": "color",
      "$value": "{color.palette.teal-700}",
      "$description": "Liens et boutons principaux"
    }
  },
  "space": {
    "m": {
      "$type": "dimension",
      "$value": { "value": 1, "unit": "rem" }
    }
  }
}
  • Le Design Tokens Community Group du W3C a publié en 2025 la première version stable de son format JSON
  • $type et $value décrivent chaque token
  • {color.palette.teal-700} est un alias : le token sémantique pointe vers le primitif
  • Des outils comme Style Dictionary le transforment en CSS, Sass, iOS ou Android
Nous écrivons nos tokens en Sass. Ce fichier montre le format d'échange.

Les primitifs dans une map

// Primitifs : les valeurs brutes de la charte, sans intention

// Couleurs
$colors: (
  "ink-900": oklch(22% 0.03 280deg),
  "ink-600": oklch(45% 0.03 280deg),
  "paper-50": oklch(98% 0.01 90deg),
  "paper-100": oklch(94% 0.02 90deg),
  "teal-700": oklch(48% 0.1 185deg),
  "coral-500": oklch(68% 0.17 40deg),
  "coral-700": oklch(52% 0.17 40deg),
);

// Espacements
$spaces: (
  "2xs": 0.25rem,
  "xs": 0.5rem,
  "s": 0.75rem,
  "m": 1rem,
  "l": 1.5rem,
  "xl": 2.5rem,
);

// Rayons des angles
$radii: (
  "s": 0.25rem,
  "m": 0.5rem,
  "l": 1rem,
  "pill": 999px,
);
  • Une map associe des clés à des valeurs
  • oklch() : luminosité, chroma, teinte. Même luminosité = même contraste perçu d'une teinte à l'autre
  • Les noms décrivent la valeur (teal-700), pas l'usage

Les tokens sémantiques

// Sémantiques : un rôle dans l'interface, relié à un primitif
$colors: (
  "text": "ink-900",
  "text-muted": "ink-600",
  "surface": "paper-50",
  "surface-alt": "paper-100",
  "primary": "teal-700",
  "on-primary": "paper-50",
  "accent": "coral-700",
  "focus": "coral-500",
);
  • Chaque rôle désigne un primitif par son nom
  • Un thème sombre serait une seconde map avec les mêmes rôles
  • on-primary : la couleur du texte posé sur la couleur primaire. Vérifiez son contraste (4,5:1 pour du texte, critère 1.4.3)

Réexporter avec _index.scss

// Point d'entrée du dossier : @use "tokens" charge ce fichier
@forward "primitives";
@forward "semantic" as semantic-*;
  • @use "tokens" charge tokens/_index.scss
  • Les deux fichiers déclarent $colors : as semantic-* préfixe ceux du second pour éviter la collision
  • On écrit ensuite tokens.$colors et tokens.$semantic-colors

Publier les tokens en custom properties

// Génère les custom properties à partir des maps de tokens
@use "index" as tokens;

@layer tokens {
  :root {
    @each $name, $value in tokens.$colors {
      --palette-#{$name}: #{$value};
    }

    @each $name, $value in tokens.$spaces {
      --space-#{$name}: #{$value};
    }

    @each $name, $value in tokens.$radii {
      --radius-#{$name}: #{$value};
    }

    // Un token sémantique pointe vers un primitif : var(), pas
    // de valeur recopiée
    @each $role, $palette in tokens.$semantic-colors {
      --color-#{$role}: var(--palette-#{$palette});
    }
  }
}
  • Quatre boucles produisent toutes les variables de :root
  • #{$value} est obligatoire : une custom property reçoit son texte tel quel
  • Le sémantique pointe vers le primitif avec var() : changer un primitif dans le navigateur met à jour ses rôles
  • Ouvrez les DevTools sur la démo : onglet Éléments, sélectionnez html

L'architecture en couches

reset · remise à zéro
tokens · custom properties
base · éléments HTML nus
layout · conteneurs, piles, grilles
components · bouton, carte…
utilities · classes d'appoint, gagnent toujours
  • @layer range les règles dans des couches ordonnées
  • Entre deux couches, la dernière déclarée gagne, quelle que soit la spécificité : .mt-l l'emporte sur .card p
  • Fini les !important et les sélecteurs à rallonge pour « gagner »
  • Les styles hors couche l'emportent sur toutes les couches : pratique pour un correctif local
Inspirée d'ITCSS : du plus générique au plus spécifique.

Déclarer l'ordre des couches

// Premier fichier chargé : il fixe l'ordre des couches.
// Une couche déclarée plus loin l'emporte, quelle que soit
// la spécificité de ses sélecteurs.
@layer reset, tokens, base, layout, components, utilities;

@layer reset {
  *,
  *::before,
  *::after {
    box-sizing: border-box;
  }

  body,
  h1,
  h2,
  h3,
  p,
  figure,
  ul {
    margin: 0;
  }

  img {
    display: block;
    max-inline-size: 100%;
  }

  @media (prefers-reduced-motion: reduce) {
    *,
    *::before,
    *::after {
      animation-duration: 0.01ms !important;
      transition-duration: 0.01ms !important;
    }
  }
}
  • La première ligne fixe l'ordre une fois pour toutes
  • Le reset est chargé en premier : l'ordre est connu avant toute règle
  • prefers-reduced-motion coupe les animations pour les personnes sensibles au mouvement
Les deux !important sont voulus : un réglage d'accessibilité doit l'emporter partout. C'est la seule exception autorisée par notre Stylelint.

Le point d'entrée

// Point d'entrée du framework, compilé en dist/ui.css
@use "base/reset";
@use "tokens/custom-properties";
@use "base/base";
@use "layout/layout";
@use "components/button";
@use "components/card";
@use "utilities/utilities";
  • Un seul fichier compilé : main.scss, sans _
  • Un @use par partial, dans l'ordre des couches
  • Chaque partial range ses règles dans sa couche : @layer components { … }
  • Les mixins et fonctions sont chargés là où on les utilise, pas ici

La chaîne qualité

Vérifier automatiquement ce qu'un œil fatigué laisse passer

Six contrôles à chaque push

Stylelint
Erreurs et conventions du CSS et du SCSS
html-validate
HTML valide et règles d'accessibilité statiques
Playwright
Régression visuelle : la page a-t-elle changé ?
axe
Accessibilité de la page rendue
Lighthouse
Performance, accessibilité, bonnes pratiques, SEO
Pages
Déploiement si tout est vert
Une intégration continue (CI) lance ces contrôles sur un serveur à chaque push. Une pull request rouge ne se fusionne pas.
Les outils ne détectent qu'une partie des problèmes d'accessibilité. Le test au clavier et au lecteur d'écran reste indispensable.

Stylelint

{
  "extends": ["stylelint-config-standard-scss"],
  "ignoreFiles": ["dist/**"],
  "rules": {
    "selector-class-pattern": [
      "^[a-z][a-z0-9]*(-[a-z0-9]+)*(__[a-z0-9-]+)?(--[a-z0-9-]+)?$",
      { "message": "Classes en BEM : bloc__element--modificateur" }
    ],
    "declaration-no-important": true
  },
  "overrides": [
    {
      "files": ["scss/base/_reset.scss"],
      "rules": { "declaration-no-important": null }
    }
  ]
}
  • Stylelint repère les erreurs (propriété inconnue, doublon) et impose les conventions
  • La config standard-scss : les règles communes, adaptées au SCSS
  • Une expression régulière impose le nommage BEM
  • overrides lève une règle pour un seul fichier
  • --fix corrige une partie automatiquement
  • html-validate se règle de même dans .htmlvalidate.json

Playwright : la configuration

import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  testDir: "tests",
  // Une seule capture de référence par test, quel que soit le
  // système (sinon Playwright ajoute -darwin, -linux…)
  snapshotPathTemplate: "{testDir}/captures/{arg}{ext}",
  expect: {
    toHaveScreenshot: { maxDiffPixelRatio: 0.01 },
  },
  use: { baseURL: "http://localhost:4173" },
  projects: [
    { name: "ordinateur", use: { ...devices["Desktop Chrome"] } },
    { name: "mobile", use: { ...devices["Pixel 7"] } },
  ],
  // Lance un serveur local avant les tests, l'arrête après
  webServer: {
    command: "npm run serve",
    url: "http://localhost:4173",
    reuseExistingServer: !process.env.CI,
  },
});
  • Playwright pilote un vrai navigateur
  • Deux projets : chaque test tourne sur ordinateur et sur mobile
  • webServer lance le site avant les tests
  • maxDiffPixelRatio tolère 1 % de pixels différents
Le rendu des polices varie d'un système à l'autre. Générez les captures de référence là où tournent les tests (la CI Linux) avec --update-snapshots.

Playwright : les tests

import { test, expect } from "@playwright/test";
import AxeBuilder from "@axe-core/playwright";

test("la page n'a pas changé d'apparence", async ({ page }, info) => {
  await page.goto("/");
  // Une capture par projet : programme-ordinateur.png…
  await expect(page).toHaveScreenshot(
    `programme-${info.project.name}.png`,
    { fullPage: true },
  );
});

test("aucune erreur d'accessibilité détectée par axe", async ({
  page,
}) => {
  await page.goto("/");
  const results = await new AxeBuilder({ page })
    .withTags(["wcag2a", "wcag2aa", "wcag21aa", "wcag22aa"])
    .analyze();
  expect(results.violations).toEqual([]);
});
  • toHaveScreenshot compare la page à une capture enregistrée. La première exécution la crée
  • Un token modifié par erreur ? Le test échoue et le rapport montre la différence
  • @axe-core/playwright audite la page rendue selon WCAG 2.2 AA

Le workflow GitHub Actions

# Contrôle qualité à chaque push et pull request,
# déploiement sur GitHub Pages depuis main
name: Qualité et déploiement

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  qualite:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build
      - run: npm run lint
      - run: npx playwright install --with-deps chromium
      - run: npm test
      - run: npx lhci autorun
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: rapports
          path: |
            playwright-report/
            lhci/
      - uses: actions/upload-pages-artifact@v3
        if: github.ref == 'refs/heads/main'
        with:
          path: .

  deploiement:
    needs: qualite
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deploiement.outputs.page_url }}
    steps:
      - id: deploiement
        uses: actions/deploy-pages@v4
  • GitHub Actions lit les fichiers de .github/workflows/
  • Un job enchaîne des étapes sur une machine Ubuntu neuve
  • En cas d'échec, les rapports sont téléchargeables dans l'onglet Actions
  • Sur main, le second job publie le site sur GitHub Pages
Dans le dépôt : Settings → Pages → Source : GitHub Actions.

À retenir

  • Dart Sass et ses modules : @use, @forward, partials. @import est déprécié
  • Sass sert à écrire le CSS (maps, boucles, fonctions, mixins). Les custom properties le font vivre dans le navigateur
  • Tokens en trois niveaux : primitifs → sémantiques → composants. Un composant n'utilise jamais un primitif
  • @layer ordonne la cascade : la couche déclarée en dernier gagne, quelle que soit la spécificité
  • Une CI verte à chaque push : Stylelint, html-validate, régression visuelle, axe, Lighthouse, puis déploiement
  • Les outils ne remplacent pas le test au clavier et au lecteur d'écran
