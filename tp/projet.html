Projet – Votre framework CSS

HTML & CSS avancés · En groupe · Du 7 au 13 décembre

En groupe, vous créez votre propre mini-framework CSS : des design tokens, une architecture en couches, des composants documentés et accessibles. Puis vous l'utilisez pour intégrer trois pages d'une maquette Figma. Chaque livraison passe une chaîne qualité automatique, comme dans une équipe front-end professionnelle.

Le projet en bref
  • Groupes de trois, formés le lundi 7 décembre. Deux binômes sont possibles pour tenir compte de l'effectif, jamais une personne seule.
  • Une maquette Figma Community par groupe, choisie dans la liste de la partie 3.
  • Il donne la note de projet, qui compte pour 50 % de la note du module. C'est la moyenne de deux notes sur 20 : la production du groupe et votre soutenance individuelle.
  • Répartition libre : chacun écrit une part réelle du code, dont au moins deux composants du framework.
  • Soutenance le jeudi 10 décembre à 17h30. Rendu : dernier commit poussé sur main le dimanche 13 décembre avant 23h59.

Un framework se juge à sa réutilisation. Si une page a besoin d'un style que le framework n'offre pas, ajoutez un composant ou une variante au framework, documentez-le, puis utilisez-le. Évitez le CSS propre à une page.

2 Les exigences techniques

Le framework

  • Design tokens relevés dans la maquette et définis en Sass (maps), puis exposés en custom properties (--color-primary, --space-m…). Les couleurs sont écrites en oklch(). Aucune valeur de couleur ni d'espacement en dur dans les composants.
  • Architecture en couches avec @layer : au minimum reset, tokens, base, layout, components, utilities.
  • Sass moderne : modules avec @use et @forward, aucun @import (obsolète depuis Dart Sass 1.80).
  • Au moins 6 composants documentés dans le guide de style (bouton, carte, navigation, formulaire, alerte, onglets, modale…). Nommage BEM, vérifié par Stylelint.
  • Au moins 2 composants interactifs en JavaScript natif ou en Web Components (menu mobile, onglets, modale avec <dialog>, accordéon, carrousel…). Ils s'utilisent entièrement au clavier et exposent les bons attributs ARIA. Aucune bibliothèque JavaScript : ni jQuery, ni Bootstrap.
  • Un thème sombre obtenu en redéfinissant les custom properties (prefers-color-scheme, avec ou sans bouton de bascule).
  • Au moins un composant qui s'adapte à son conteneur avec une container query.

L'intégration

  • HTML sémantique : régions (header, nav, main, footer), un seul h1 par page, titres sans saut de niveau, formulaires étiquetés, images avec un texte alternatif pertinent (ou vide si elles sont décoratives).
  • Fidélité à la maquette sur ordinateur : couleurs, typographie, espacements, alignements.
  • Responsive du mobile (320 px) au grand écran, sans défilement horizontal. Typographie fluide avec clamp(). Si la maquette n'a pas de version mobile, vous la concevez.
  • Performance : images responsives (srcset, sizes, format AVIF ou WebP), polices auto-hébergées en WOFF2, aucune ressource bloquante inutile.
  • Le pied de page cite la maquette : son titre, son auteur, son lien et sa licence.

L'accessibilité et la qualité

  • Niveau WCAG 2.2 AA : contrastes suffisants, focus toujours visible, lien d'évitement, navigation complète au clavier, prefers-reduced-motion respecté.
  • Une page testée au lecteur d'écran (VoiceOver sur macOS, NVDA sur Windows) : notez dans le README ce que vous avez vérifié.
  • Chaîne qualité lancée à chaque push par GitHub Actions et verte sur main :
    • Stylelint et html-validate sans erreur ;
    • tests Playwright : régression visuelle (toHaveScreenshot) de chaque page sur mobile, tablette et ordinateur, aucune violation axe, aucun débordement horizontal ;
    • Lighthouse CI avec ces seuils : performance 90, accessibilité 95, bonnes pratiques 90, SEO 90.
  • Déploiement automatique sur GitHub Pages après chaque push sur main.

Les seuils et les tests sont déjà configurés dans le dépôt modèle. Vous ne les abaissez pas : vous améliorez votre code jusqu'à ce qu'ils passent.

Valorisé (bonus)

  • Des transitions de page avec l'API View Transitions.
  • Une infobulle ou un menu positionné avec l'anchor positioning et l'API Popover.
  • Des tests Playwright du comportement des composants interactifs (clavier, ARIA).
  • Le framework publié comme paquet npm, utilisable dans un autre projet.

4 Le dépôt modèle

Partez du dépôt modèle (projet-modele.zip). Il contient la chaîne qualité complète, un squelette Sass en couches, deux composants d'exemple et un Web Component. Vous le remplacez progressivement par votre framework. 


      .github/workflows/qualite.yml   Lint, tests, Lighthouse puis déploiement
      scripts/build.mjs               Compile le Sass et construit dist/
      scripts/serve.mjs               Sert dist/ sur http://localhost:4173
      src/
        index.html                    Première page intégrée
        style-guide.html              Guide de style du framework
        js/main.js                    Charge les composants interactifs
        js/components/                Un fichier par composant interactif
        scss/main.scss                Point d'entrée du framework
        scss/_layer-order.scss        Ordre des couches
        scss/abstracts/               Tokens (maps Sass) et mixins
        scss/layers/                  reset, tokens, base, layout, utilities
        scss/components/              Un fichier par composant
      tests/pages.js                  La liste des pages testées
      tests/visuel.spec.js            Régression visuelle
      tests/accessibilite.spec.js     axe et débordement horizontal
      lighthouserc.json               Seuils Lighthouse
      .stylelintrc.json               Règles Stylelint (BEM, pas d'!important…)
      .htmlvalidate.json              Règles html-validate (dont accessibilité)
  1. Décompressez l'archive, puis créez avec elle un dépôt GitHub public nommé framework-nom1-nom2-nom3 (public pour publier gratuitement sur GitHub Pages).
  2. Dans Settings → Pages, choisissez la source GitHub Actions.
  3. Installez et lancez le projet : 
    
          npm install
          npx playwright install chromium
          npm run dev
  4. Dans l'onglet Actions, lancez le workflow « Qualité et déploiement » en cochant Mettre à jour les captures. Les captures de référence de la régression visuelle sont produites sur le serveur Linux de GitHub, pas sur vos ordinateurs : relancez-le ainsi après chaque changement visuel voulu.
  5. Ajoutez chacune de vos pages dans tests/pages.js.
Le test visuel échoue alors que je n'ai rien cassé

Si le changement est voulu, régénérez les captures avec le workflow. S'il ne l'est pas, téléchargez l'artefact rapport-playwright du workflow : il montre la capture attendue, la capture obtenue et leur différence.

8 L'IA générative

  • L'IA (ChatGPT, Claude, Copilot…) est autorisée pour le projet.
  • Chaque membre doit comprendre et savoir expliquer l'ensemble du code. Un composant que personne ne sait expliquer pendant la soutenance n'est pas compté.
  • Déclarez votre usage dans le README : quels outils, pour quelles tâches, ce que vous avez vérifié ou réécrit.
  • Méfiez-vous des réponses qui datent : @import en Sass, préfixes -webkit- inutiles, float pour la mise en page, jQuery, outline: none sans remplacement. Les outils de la CI en repèrent une partie.
  • L'IA est interdite à l'épreuve individuelle sur machine : le projet est le bon moment pour apprendre à écrire ce code vous-mêmes.
